## LLM到GPU模式：-t不能解释成GPU线程数量

`transformers/llm/engine/src/llm.cpp:41–60` 的 `backend_type_convert("opencl")` 返回3；`"qnn"`返回16，`"hexagon"`返回10，`"npu"`返回NN=5，不能混用。

`Llm::initRuntime` (`llm.cpp:237–271`) 把thread_num放入ScheduleConfig.numThread；对于OpenCL，`:243–247`自动OR 64和512。`llm_bench.cpp:1145–1150`只是把CLI的-t请求值传为thread_num。

`include/MNN/MNNForwardType.h:69–85`定义：

- 4 = MNN_GPU_TUNING_WIDE；
- 64 = MNN_GPU_MEMORY_BUFFER；
- 512 = MNN_GPU_RECORD_BATCH。

本轮请求4，**LLM最终传递580=4|64|512**。它表示Wide tuning、Buffer模式和批量录制请求，不是580线程或4个GPU worker。CPU oracle保持4，不能把GPU编码复制给CPU。

`OpenCLBackend::setGpuMode` (`OpenCLBackend.cpp:1728–1796`) 解码这些位。未指定内存类型时Adreno通常选Image，但LLM已经强制Buffer；录制还要满足设备扩展和队列容量条件，不能只由512推定实际启用。只用-t4即可，不需要把技能中的68/516示例机械叠加。`Llm::tuning` (`llm.cpp:495–511`) 对OpenCL直接return，其旁边的旧KVMeta TODO不能代替对当前Attention/KV实现的阅读。

## 回退路径和支持机制

1. `Schedule::getAppropriateType` (`source/core/Schedule.cpp:111–155`) 可在找不到runtime creator或不能创建时选择backupType；这是后端级回退。
2. `Session.cpp:31–59`建立主backend及CPU backup。
3. `Pipeline.cpp:538–600`创建execution，`:589–596`主backend返回nullptr后尝试CPU backup；两者都失败才NOT_SUPPORT。
4. `OpenCLBackend::onCreate` (`OpenCLBackend.cpp:674–779`) 按(opType,Buffer/Image)找creator；int8输入、缺creator、Image尺寸限制或creator拒绝都可返回nullptr。编译宏OPENCL_FALLBACK_LOG输出这些拒绝原因/节点名，本轮仅诊断构建启用。
5. creator成功不表示所有后续分配/resize都一定成功；Pipeline还存在执行/resize和运行时错误路径。不能把“没看到fallback日志”升级成任何上下文下100%无CPU。

CPU上的Tokenizer、采样、图shape/常量计算、资源管理不等于“模型整体静默CPU回退”。本轮证明主要模型计算在GPU执行，并记录未见Creator回退；没有宣称整个进程没有CPU工作。

## 哪些执行路径已被实际事件支持

- `ConvBufLowMemoryExecution.cpp:321–323,464–466`读取固定模型quanParameter/aMaxOrBits；`onExecute` (`1760–1815`) 的诊断分支真实enqueueNDRangeKernel并pushEvent。标签 `Convolution0`是op类型+unit索引，不是精确CL_KERNEL_FUNCTION_NAME。
- `AttentionBufExecution.cpp:1587–1660`建立flash_decode_partial/reduce；`:1878–1884`记录Prefill/rearrange事件；`:1916–1921`实际提交Decode partial/reduce并记录事件。
- `OpenCLBackend::onExecuteBegin/End` (`OpenCLBackend.cpp:809–825`) 清理前次事件、提交本次执行并printEventTime；`OpenCLRuntime.cpp:1443–1528`等待事件，读取CL_PROFILING_COMMAND_START/END并输出。它们是设备queue事件，不只是host callback墙钟，也不是仅启动时的驱动查询。
- 自然输入21 Token、生成16 Token的诊断烟测中，Convolution事件3349=197×17，flash_attention_prefill28，flash_decode_partial和reduce各448=28×16。这与真实模型197个线性层/28层Attention及1次Prefill+16次Decode对应，排除了“只有驱动小测试或初始化GPU、LLM全在CPU”的解释。

完整标签/数量及非零事件数在 `analysis/gpu-event-counts.csv`。未用事件耗时建立性能基线。**诊断宏会绕过部分record-queue路径并逐事件等待**，见Conv的`:1761–1768`与Attention的`:1923–1930`；不能把诊断模式和clean模式当作完全相同的提交策略。

## 配置路径与错误识别

`LlmConfig` (`llmconfig.hpp:88–105,108–113,132–134`) 直接做base_dir+文件字段拼接，不自动识别每字段的绝对路径。首次新配置错误地给llm_model/weight/tokenizer绝对路径，形成`.//data/...`，初始化失败。修正为 `base_dir=原固定模型目录/`、文件字段相对名；模型字节没有改变。

`llm_demo`这次初始化失败仍退出0，因此脚本/分析同时检查错误标记和实际生成Token统计；初次失败raw完整保留，`runtime-analysis.json`明确判为失败。首次不存在的tuning cache打印Load Cache file error随后成功生成，是cache miss，不与LLM init error混判。

## 数值入口及边界

`Llm::getOutputs` (`llm.cpp:1451–1453`) 返回当前生成参数输出，`response(ids,...,0)`可只做Prefill；本轮确实取得了两个输入各151936个float32 host logits，shape一致且全finite。两后端不要求逐字节一致，实际初筛标准和未通过结果另见[正确性计划](GPU正确性对照计划.md)。

CPU低内存量化路径 `ConvInt8TiledExecutor.cpp:2394–2418`含输入动态量化；OpenCL是另一套低内存权重/浮点kernel执行路径。它们的计算顺序/中间精度差异是后续调查假设，不是本轮Logits偏差的已证实原因。不能从Top1相同推导数值验证通过，也不能直接将偏差归为GPU kernel Bug。
