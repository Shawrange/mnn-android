Prefill logits产生第一个输出token。每个输出token仍被送入一次forward，因此N个生成token有N次Decode forward；最后一次计算的下一token logits未再采样。吞吐不是“首token到第N个token”的直接流式速度，也不是TTFT。

`Llm::updateContext` (`src/llm.cpp:846–849`) 分别累计all_seq_len/gen_seq_len。history_tokens是Token历史；KVMeta::previous是已执行forward的逻辑KV长度，两者不能混用来推定每一时刻的缓存状态。

## 2. 单步 forward → 执行器

`Llm::forwardVec(vector<int>)` (`src/llm.cpp:732–736`) 包含单token embedding。VARP重载 (`739–754`) 在本配置chunk=0时设 `mMeta->add=seq_len`，构造mask/position，调用forwardRaw。

`Llm::forwardRaw` (`592–651`) 按Decode状态与序列长度选择module；`633`调用onForward，`641–647`读取/检查输出，`649–651`同步等待；`708`调用KVMeta::sync。此路径在原Decode Timer内。同步完成保证计时覆盖CPU计算，不是仅提交任务。

图执行层的源码连接为 `StaticModule::onForward/_execute` (`express/module/StaticModule.cpp:783–834`) → `Session::run` (`source/core/Session.cpp:271–286`) → `Pipeline::execute` (`source/core/Pipeline.cpp:1173–1235`) → `cmd.execution->onExecute` (`1208`)。上层module可有组合/clone，以上是执行子图到backend的连接，不称为采样得到的完整栈。

`source/core/KVMeta.hpp:48–61`，`KVMeta::sync`：

```
previous = previous - remove + add + sum(reserve sizes)
remove/add/reserve reset
```

当前每步add=1、remove=0、无reserve；公开 `Llm::getCurrentHistory` (`src/llm.cpp:917–919`) 返回previous。诊断记录步骤前后此值，并用每步28次Attention/28次KV更新覆盖检查。不是以输出token数猜KV长度。

从128输入开始，普通onAlloc容量为192；前64步达到192无需扩容。第65步所需193超过192，容量变为257；下一次是第130步（258→322），再下一次第195步（323→387）。这是64个Token余量导致65步间隔，不能写成“每64步必然扩容”。原始事件还能验证每层past、容量与inDisk；不代表具体OS allocator调用次数。

## 4. 如何读取历史KV

`CPUAttention::onExecute` 在追加后读取manager.kvLength (`CPUAttention.cpp:490–496`)，得到含当前token的kvSeqLen。当前decode分组以GQA组织查询头 (`508–529`)；Flash logical block在多线程浮点KV满足pack约束时可取256，实际mKvBlockSize=min(blockCap,kvLength) (`456–485`)。这不是新的KV Cache架构。

按线程划分的执行函数里，`825`计算kvBlockNums；`runBlocks` (`902–1390`) 由 `931–934`取得当前KV head地址，`953`遍历该线程负责的历史KV块，`955`附近截断尾块到实际有效kvSeqLen。未量化K路径 `1059–1091`做QK；`1116–1141`做softmax/Flash统计；浮点V路径 `1234–1338`按V物理子块做PV并累计。`1394–1443`处理KV分片/头分配；`1469`join同步。

因此每一步只有新token的K/V需要追加，但Attention仍需访问历史有效KV，长序列可提高Attention成本；Flash attention控制临时块和归一化，不会把历史读取复杂度变成常数。容量增长、块边界、pack/GQA与调度都可能叠加在趋势上。具体耗时占比必须以Trace验证，不能从渐近复杂度直接推出端到端降幅。

## 5. 工具与观测局限

- `llm_bench`已有 `BenchProfile` (`tools/llm_bench.cpp:1200–1277`) 使用steady_clock，可按prefill/decode聚合op；只在首调用记录shape，不提供逐token实际KV或增长事件，debug callbacks还会改变执行路径。没有将它直接作为Token Trace。
- 原生 `Timer` 在Android分支用gettimeofday (`source/core/AutoTime.cpp:31–56`)，有系统时钟调整限制；本诊断不替换它，另用CLOCK_MONOTONIC对照。
- JSON (`tools/llm_bench.cpp:589–608`) 保存阶段TPS均值/标准差；`TestInstance::getTokensPerSecond` (`224–237`) 按每次Token数/微秒×1e6计算；聚合均值/样本标准差实现位于 `147–163`。`-rep1`原std=0只是一个有效测量。
- 插桩只在ArGeneration普通Decode循环激活，prefill和tuning分配不记录；Attention scope包括KV scope，不能相加。KV scope只区分alloc/realloc/update函数，并不进一步拆分memcpy、页错误、pool或系统分配时间。
- 主线程CPU时钟排除worker CPU，不能当作全模型CPU利用率；Attention墙钟包括等待worker、系统抢占等，不是纯kernel硬件周期。
